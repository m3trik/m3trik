- **`push.ps1` — no more "phantom publishes" when re-running a cascade over a package with no real changes (2026-07-01).** Two coupled defects. (1) Step 4 (Merge to Main) was gated only on the `-Merge` flag, so it ignored the `$needsMerge = $false` that step 2 sets — the `"Dev is ahead only due to dev bump (skipping merge)"` message was a no-op, and step 4 merged the bumped version to main anyway, tripping `publish.yml` into shipping an unintended release (observed: `pythontk 0.8.77` auto-published to PyPI on a cascade re-run with no pythontk changes), then **mis-tagged** because `$localStrictVersions` still held the previous version — leaving an *untagged* PyPI version that violates the publish→tag→release invariant. Step 4 now gates on `$Merge -and $needsMerge`. (2) But `$needsMerge` alone was unsafe: `Test-OnlyDevBumpChanges` listed `pyproject.toml`/`README.md` as "bump-only" files, so a **dependency-cascade release** (whose only change is the upstream pin in `pyproject.toml` + the version) would have been classed as skippable and its merge dropped — silently defeating the whole point of the cascade. Since all four strict packages use dynamic versioning (`version = {attr = "<pkg>.__version__"}`), a pure bump touches **only** `<pkg>/__init__.py`; the allow-list is narrowed to exactly that. Net: a version-only bump skips (no phantom); a pin/doc/code change keeps `$needsMerge = $true` and merges + propagates as before. (The one phantom `0.8.77` was retroactively tagged + released by hand to restore the invariant.)
