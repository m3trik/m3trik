- **2026-08-20 — `Test-PRReleaseGate` NAMES the failing checks that do not block the merge (`push.ps1`).** `Get-PRGateState` reduced `statusCheckRollup` to two facts — how many checks are attached and how many are still running — and never looked at a settled check's `conclusion`. A workflow that reports FAILURE while not being a *required* check leaves `mergeStateStatus` CLEAN, so the gate printed `OK PR #N is gated by 3 check run(s)` and armed auto-merge over a red PR. Measured on the live repos: the **Validate Publish Chain** jobs `validate-tentacle` and `summary` were FAILURE on pythontk PRs **#48 and #49**, and both released green. The gate now collects every settled check whose conclusion is not SUCCESS/NEUTRAL/SKIPPED (plus StatusContext nodes in FAILURE/ERROR, which carry `context` rather than `name`) and lists them by name. The report is emitted **before** the `BLOCKED` branches, not on the plain-success path — the transient "BLOCKED, checks still running" case also returns success, so a report placed after it would still have shipped a red check unmentioned on the most common path of all. Deliberately **not** fatal: whether a red check may block a merge is branch protection's call, and GitHub already enforces it for required checks by holding the PR at BLOCKED — which this gate has refused since 2026-08-17. Making a non-required failure fatal here would instead hand push.ps1 a veto that the repo's own settings deliberately withheld. So the fix is reporting, not blocking: the operator sees which checks are red at the moment auto-merge is armed, instead of a green run log over a red PR. `test_push.py::test_pr_mode_surfaces_a_failing_non_required_check` drives the real script through the `gh` shim with a CLEAN rollup of one SUCCESS and two FAILUREs, and asserts BOTH halves — the release still completes (`PR #7 merged`, exit 0) and both failing names appear. It fails against the pre-fix script on the name assertion, so it is not vacuous. `test_pr_mode_names_a_failing_check_while_others_still_run` pins the placement specifically: a BLOCKED rollup of one IN_PROGRESS and one FAILURE, which goes red when the report is moved back onto the success path (verified by doing exactly that), proving the branch coverage rather than assuming it. `test_pr_mode_proceeds_when_pr_is_actually_gated` gained the counterweight — an all-green rollup must NOT print the report — because without it a check wrongly classified as failing would pass unnoticed.

- **2026-08-20 — `Get-TreeHash` pins UTF-8 while reading git, so a receipt is portable between hosts (`push.ps1`).** PowerShell DECODES a native command's stdout using `[Console]::OutputEncoding`, and `Get-TreeHash` hashes `git status` / `git diff HEAD` as text — so any non-ASCII in the diff (em-dashes and arrows, which every `CHANGELOG.md` here is full of) decoded differently per host and produced a different hash for an identical tree. That is what made a receipt recorded from an interactive console fail the gate when push.ps1 ran under `Start-Process -WindowStyle Hidden`. Measured on the real pythontk tree: the pre-fix code returned **three different hashes** — `d8de040df5df` under UTF-8, `4cab1b3edda9` under Windows-1252, `fa231cc3bfae` under CP437 — and the PowerShell tool's own default is CP437, so the gate was broken in this very environment. git emits UTF-8, so the function now pins `[Console]::OutputEncoding` to BOM-less UTF-8 for its reads and restores the host's setting in `finally`; a host that refuses the set (redirected stdout) is left exactly as before rather than throwing. All four hosts now agree on the UTF-8 value. `test_push.py::test_tree_hash_is_stable_across_host_console_encodings` pins it under captured (redirected) stdout with em-dashes, an arrow and an accented word in an uncommitted `CHANGELOG.md` edit — and fails with `3 != 1` against the pre-fix function, so it is not vacuous.

- **2026-08-19 — `check_temp_artifacts.py` also sweeps for stray artifacts already sitting in a package tree.** The gate read code for allocations that leak, which by construction cannot see an artifact with no code behind it: `pythontk/pythontk/prof` and `pythontk/p` were cProfile dumps of `geo_utils/uv_transfer.py` that a bare `-o` dropped into the importable package and the repo root, and `tentacle` carried two `.bak` files from 2026-07-19 (byte-identical to committed revisions, so nothing was lost deleting them). All four were invisible to every existing check and to `git status` habit alike. A file under `<pkg>/<pkg>/` is now legitimate only if Python loads it (`.py`/`.pyi`/`py.typed`) or the project DECLARES it as shipped data; extension-less files at a repo root are flagged too, against a sentinel set (`LICENSE`, `Makefile`, …), because that is precisely where a mistyped `-o` lands. Declaration is read from BOTH `[tool.setuptools.package-data]` and `MANIFEST.in`: package-data alone flagged all 154 of uitk's icons, which ship via the manifest only — and a gate that noisy is one nobody runs twice. Using declaration as the yardstick also makes the check self-maintaining, since a new data type must be declared for the wheel regardless. Packages declaring neither (`comfyui`) are skipped rather than guessed at: with no contract there is nothing to check against. Rejected: a `.gitignore` entry — it hides the file from `git status` while leaving it in the package tree, which inverts the actual cost, since an undeclared data file is one that is silently ABSENT for every installed user. Measured after the sweep: 4 strays across 7 declared packages, 0 false positives.

- **2026-08-19 — two release pre-passes: refuse to release while behind `origin/dev`, and name the concurrent writer behind a failed receipt gate (`push.ps1`).** (1) Every `rev-list` in the script measured `origin/dev..dev` — AHEAD. Nothing ever measured the reverse, yet being BEHIND is the normal resting state: the bump-version and API-registry bots push to `dev` after every release. So a release started against a stale local branch looked perfectly healthy, rewrote every tree, and only then failed at push. Measured 2026-08-19: all five cascade repos sat 2 commits back simultaneously and nothing in the tooling said so — a human noticed. The check is deliberately NOT under `-SkipReview`: that flag waives the review RECEIPT, and whether the remote has moved is a fact no review can settle. It also tells you to pull BEFORE recording receipts, since a pull changes the tree and voids anything recorded against the old one. (2) The receipt hash already covers the working tree, so a concurrent editor invalidates it and the gate correctly refuses — but it printed the same "no tests receipt" text it uses for a suite that was simply never run. Those two have opposite fixes (wait vs. run), and the natural response to the ambiguous message is to re-run and re-record, which races the other writer and can pin a receipt to a tree that is still moving; `-Merge` then does `git add -A` and publishes their in-progress work to PyPI, unrecallably. The failure now lists changed files whose mtime is under 15 minutes, excluding generated `API_*` sidecars — regenerating those immediately before a release is the normal flow and would have made every clean release look like a collision. Rejected: a TOCTOU re-check of the tree hash just before `git add .` — push.ps1 legitimately rewrites `pyproject.toml` and `__init__.py` in between, so the hash always moves and the guard would be either useless or permanently red. Both run before any mutation, so failing costs nothing.

- **2026-08-19 — the pin sync may RAISE a dependency floor, never lower it (`push.ps1::Sync-PyProjectDepsToLocalVersions`).** `Get-LocalStrictVersions` clamps every version down to what PyPI actually publishes, and the sync then rewrote the downstream pin to it unconditionally — so a run that did NOT include the upstream walked a deliberately raised floor back to the old release. Measured 2026-08-19: with mayatk correctly declaring `pythontk>=0.9.25` (its `task_manager` reads `MapOptimizer.SIZE_CLAMP_TEMPLATE` in a CLASS BODY, so an older pythontk is an AttributeError at IMPORT, not at first use), `push.ps1 -Packages mayatk` alone would have rewritten it to `>=0.9.24` and shipped the crash the raise existed to prevent. A floor states what the CODE needs; the sync only ever ratchets it up to the version it is publishing, and says so when it keeps the higher one. The full cascade was always safe — upstream publishes first, so the map already held the new version — which is exactly why this stayed invisible. Regression test drives the real script through a temp cascade with the floor above the published version.

- **2026-08-18 — `test_pinned_versions_exist_on_pypi` stopped failing for the length of every cascade (`test/test_push.py`).** `Sync-PyProjectDepsToLocalVersions` writes each internal pin from the sibling's LOCAL version, and the cascade publishes upstream-first — so between the pin sync and the upload a downstream legitimately pins a version PyPI does not have yet. A pin whose version the workspace actually holds (working tree or `origin/dev`) is now reported as a pending publish rather than failed; a pin naming a version nobody has still fails, because that one can never resolve. The `__version__` parse both this and `test_versions_are_valid_semver` needed is now one module-level `version_in`, on the loose pattern — the semver check has to SEE a malformed version to reject it, so a stricter regex would have hidden the very thing it looks for.

- **2026-08-08 — `package-manager.bat` repainted in 24-bit pastels, and its warning markers were invisible the whole time.** The menu was drawn with `Write-Host -ForegroundColor <name>`, which can only reach the 16 legacy console colors — a palette with no pastel range at all, so the look could not be modernized without changing the mechanism. Output now carries 24-bit ANSI SGR sequences (mauve title/banner, blue + sky menu keys, green/yellow/peach/red status, lavender prompts) defined once as a `C_*` palette block near the top rather than spelled out per line; cmd.exe turns on VT processing for its console on Win10+ and the `powershell` children write to that same screen buffer, so it renders in conhost and Windows Terminal alike. - **`push.ps1` — no more "phantom publishes" when re-running a cascade over a package with no real changes (2026-07-01).** Two coupled defects. (1) Step 4 (Merge to Main) was gated only on the `-Merge` flag, so it ignored the `$needsMerge = $false` that step 2 sets — the `"Dev is ahead only due to dev bump (skipping merge)"` message was a no-op, and step 4 merged the bumped version to main anyway, tripping `publish.yml` into shipping an unintended release (observed: `pythontk 0.8.77` auto-published to PyPI on a cascade re-run with no pythontk changes), then **mis-tagged** because `$localStrictVersions` still held the previous version — leaving an *untagged* PyPI version that violates the publish→tag→release invariant. Step 4 now gates on `$Merge -and $needsMerge`. (2) But `$needsMerge` alone was unsafe: `Test-OnlyDevBumpChanges` listed `pyproject.toml`/`README.md` as "bump-only" files, so a **dependency-cascade release** (whose only change is the upstream pin in `pyproject.toml` + the version) would have been classed as skippable and its merge dropped — silently defeating the whole point of the cascade. Since all four strict packages use dynamic versioning (`version = {attr = "<pkg>.__version__"}`), a pure bump touches **only** `<pkg>/__init__.py`; the allow-list is narrowed to exactly that. Net: a version-only bump skips (no phantom); a pin/doc/code change keeps `$needsMerge = $true` and merges + propagates as before. (The one phantom `0.8.77` was retroactively tagged + released by hand to restore the invariant.)
- **`generate_api_registry.py` / `check_context_budget.py` — `--check` ignores the cosmetic generation date (2026-07-01).** The `_Generated: <date>_` markdown line (and the JSON `"generated_at"` field) made every *untouched* registry read as "stale (would be rewritten)" the moment the day rolled over — so a cascade on a new day recurringly failed the budget gate and forced a date-only re-commit of packages that hadn't changed. Real content changes are still caught (they differ in more than the date).
- **`generate_api_registry.py` — deterministic module ordering across platforms (2026-06-27).** `_iter_py_files` sorted `Path` objects, but `WindowsPath` compares case-insensitively while `PosixPath` (CI/Linux) compares case-sensitively — so a local (Windows) regen ordered same-prefix modules differently from CI (e.g. `table_actions.py` vs `tableWidget.py`), making committed registries drift between local and CI runs and recurringly tripping `check_context_budget.py --check` after a cascade. - **`push.ps1` — every publish now creates an annotated `vX.Y.Z` git tag + a GitHub Release (2026-06-27).** Closes the gap where the curated `CHANGELOG.md` lived only as a file on a branch, never attached to anything git-native. After the dev→main merge + successful publish workflow, `push.ps1` tags the released `origin/main` commit `vX.Y.Z` (idempotent — skips if the tag already exists) and, when this release added CHANGELOG entries, cuts a GitHub Release whose notes are exactly those additions. Notes come from `Get-ChangelogDelta` = the lines added to `CHANGELOG.md` on dev vs the last-released `origin/main` (`git diff origin/main..dev`) — a deterministic boundary needing **no** change to the existing dated-prose changelog (no `[Unreleased]` section, no commit-message convention). A release that added no CHANGELOG entries (docstring-only / dependency bump) is still tagged, just without a Release body. The tag/Release step is additive and **non-fatal** — it runs only after PyPI publish + main merge already succeeded, so a `gh`/tag hiccup can never abort a release (add the tag manually if so). `common.ps1` `Merge-ToMain` also now auto-resolves a `CHANGELOG.md` merge conflict by taking dev's copy (the post-release state is always dev's), matching the existing `__init__.py`/`pyproject.toml` handling. The stamp/`[Unreleased]` model was evaluated and rejected: the repo's changelogs are richly hand-curated dated prose, and a `git diff` boundary delivers the same git-native Release with zero disruption to that habit.
