# C#

How the principles are spelled in C#, as Unity 6.3 and newer compiles it; the rationale is CODE_STANDARD (`§N`). A product's shapes (its parts, where its actions live, its doors) are in its repo's AGENTS.md.

- **Version and style** (§1, §2): C# 9 as Unity compiles it: no init-only setters, covariant returns or module initializers; a `record` needs the `IsExternalInit` shim and never enters a serialized type. Style is the .NET coding conventions in `.editorconfig` plus Microsoft.Unity.Analyzers, applied at review, not while prototyping. Public members carry XML doc comments (`<summary>` first, then `<param>`, `<returns>`, `<exception>`); text a front end shows comes from attributes (`[Tooltip]`), since reflection cannot read comments.
- **Naming and layout** (§3): PascalCase types, methods, properties, events and constants; camelCase public and serialized fields (the inspector's convention), parameters and locals; `_camelCase` private fields. One top-level type per file, named after it. A new type sits in the namespace its assembly is named for (`M3trik.<Package>.<Part>`); a type already in the global namespace moves only with its part's planned split, since a namespace move breaks project scripts.
- **Parts are assemblies** (§0, §4): references point down the order the repo declares in `[tool.m3trik.layers]`; a compile error from reaching a peer is fixed with a contract, never a new reference. `internal` by default; `public` only for what other parts call, and that surface is published (§5).
- **Inject, never reach** (§14): a collaborator arrives as an interface, through the constructor for a plain class, as a parameter for an action (defaulting to its registered provider), and through Unity's own lookups for a component (`GetComponent<IThing>()`), which Unity constructs itself; a host seam is an interface with a `Pure*` stand-in. Never find a type by a name in a string (`Type.GetType`, `GetComponent("X")`).
- **Loading does no work** (§4): a static constructor, `[InitializeOnLoad]` or `[RuntimeInitializeOnLoadMethod]` only registers. No mutable static state but a registry its owner rebuilds after a domain reload; never a Unity object in a static.
- **Unity objects** (§1, §15): never `?.`, `??` or `is null` on a `UnityEngine.Object`, which skip Unity's destroyed-object check; write `== null` (UNT0007, UNT0008, UNT0029). Unity's API runs on the main thread only; a worker hands its result back.
- **Saved data** (§5): serialized field names, script GUIDs and asset paths are published: rename a field with `[FormerlySerializedAs]`, move a file with its `.meta`, and commit every new file with its `.meta`. No `[SerializeReference]` in saved data: it stores the type's name, and its rename fix (`[MovedFrom]`) is undocumented.
- **Editor code** (§14, §15): it lives in an editor assembly; `#if UNITY_EDITOR` in a runtime file only around a member Unity calls in the editor (`OnValidate`, `Reset`). It changes serialized data through `SerializedObject`, or records the change for undo first (`Undo.RecordObject`, or the wrapper the repo's AGENTS.md names), so undo, prefab overrides and multi-object editing work.
- **Actions**: what a feature lets people and agents do is a public static method, as Python's is a function: plain values in and out, documented by XML comments, and an optional `OpContext ctx` it asks before each change (`ctx == null || ctx.ShouldChange(...)`; `ShouldCreate`, `ShouldDelete`, `ShouldWrite`), the C# spelling of `should_*`. Menus and windows call it; agents reach it through `unity.csharp.exec`. It is never wrapped as an operation: only the kernel declares `[Operation]`s (its exec, view and doctor), and outcomes and issues are the shared contract's generated types.
- **Generated and ported code** (§0): a contract other languages read is declared in Python and generated here as `*.g.cs`, never edited (change its source and regenerate); a model ported from Python is pinned by its reference's golden cases (`ptk.Conformance`).
- **Renames and removals** (§5): a renamed or removed public name gets a moved-names row, a CHANGELOG line and a minor bump; only where project scripts need a window does a forwarding member marked `[Obsolete("Use <new>; removed in <version>.")]` keep the old name working. A namespace move has no alias at all.
- **Prior art** (§15): what a new part weighed, and why it was or was not adopted, sits in its main type's `<remarks>` under `Prior art:`.
- **Errors** (§8): throw a specific exception whose message names the fix; catch only what you handle, never an empty `catch`; a refusal is a named warning and a skipped result.
- **Performance and files** (§7, §10): per-frame code allocates nothing (no LINQ, closures, boxing or string building in `Update` and its kin). In the editor a file's home follows its lifetime: scratch from `FileUtil.GetUniqueTempPathInProject()`, a rebuildable cache under `Library/<package>/`, settings under `ProjectSettings/`, content under `Assets/`; a player writes only under `Application.persistentDataPath` or `Application.temporaryCachePath`. Dead code is deleted, never commented out or fenced in `#if false`.
- **Tests** (§9): NUnit throughout; code with no engine reference runs under `dotnet test` without Unity, engine code under the Unity Test Framework (Edit Mode unless it needs the player loop); one `<Type>Tests` class per type, in the part's own test assembly.
